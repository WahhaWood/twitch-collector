# Twitch Auto-Collector — MVP-план (адаптированный)

> Основа: `plan.md` (v1.0). Этот документ — урезанная версия под реальные условия:
> сервис для нескольких знакомых, бесплатный хостинг (Vercel Hobby + GitHub Actions + Postgres free tier),
> вход по личному токену, объём MVP — аккаунты + прогресс дропсов/значков.
> Статус: рабочий документ, решения помечены как **(решено)** или **(предложено)**.

---

## 1. Цель MVP

Знакомые (до ~10 человек) заходят на сайт по личному токену, подключают свои Twitch-аккаунты (до 5 на человека),
и видят в одной панели: какие дропсы и значки доступны, сколько осталось до награды, когда последний раз обновлялось.

Что **не** делаем в MVP: баллы канала, серии просмотра, покемонов, приоритетные каналы и live-статус,
Web Push, Telegram, WebSocket, отдельные workers, очереди, Redis, Kubernetes.

Ограничения из `plan.md` сохраняются: не имитируем просмотр, не выдаём награды, не меняем состояние Twitch от имени пользователя.

## 2. Стек и хостинг

| Область | Решение | Почему |
|---|---|---|
| Web + API | **Next.js (App Router), TypeScript** на Vercel Hobby | UI и API в одном проекте, OAuth callback — обычный Route Handler |
| UI-стиль | Tailwind + shadcn/ui | Как в плане, без изменений |
| Данные на клиенте | SWR, polling каждые 60 с + кнопка «обновить» | Вместо WebSocket |
| БД | **Postgres на Neon** (free tier) | Serverless-драйвер, работает из Vercel-функций |
| ORM | Drizzle (предложено) или Prisma | Миграции в репо, типы из схемы |
| Синхронизация | **GitHub Actions** по расписанию → `POST /api/internal/sync` с секретом | Бесплатный cron; Vercel Hobby не даёт частый cron |
| Шифрование токенов | AES-256-GCM, ключ в env (`TOKEN_ENC_KEY`) | Envelope/KMS — избыточно для MVP |
| Логи/ошибки | Логи Vercel + Sentry free (опционально) | Prometheus/Grafana не нужны |

Почему не Python/FastAPI из плана: на Vercel Python тоже работает, но Next.js покрывает и UI, и API, и OAuth
без двух проектов. Если предпочитаешь Python — меняется только слой API, схема остаётся.

## 3. Вход по токену

**(решено)** Личный токен, выдаётся приложением. Пароли, регистрация по email и Argon2 не нужны.

1. Администратор (ты) создаёт пользователя командой/скриптом: `npm run user:create -- --name "Вася"`.
   Скрипт печатает токен один раз.
2. В БД хранится только `sha256(token)` (таблица `users.token_hash`), сам токен не сохраняется.
3. Вход: поле «Токен» → `POST /api/auth/login` → сервер находит пользователя по хэшу → ставит cookie.
4. Cookie: `HttpOnly`, `Secure`, `SameSite=Lax`, подписана HMAC (`SESSION_SECRET`), TTL 30 дней.
5. Выход: `POST /api/auth/logout` очищает cookie. Перевыпуск токена — тем же скриптом (старый хэш перезаписывается).
6. Brute force: простой лимит на `/api/auth/login` по IP (таблица или Vercel KV/Upstash free).

Все API-маршруты, кроме `login` и `internal/sync`, проверяют cookie и фильтруют данные по `user_id`.

## 4. Twitch-интеграция

### 4.1. Подключение аккаунта (OAuth)

Authorization Code + PKCE (как в плане, раздел 6.1), но без отдельной таблицы состояний в БД:
- `state` и `code_verifier` кладутся в короткую подписанную cookie (TTL 10 минут);
- callback сверяет `state`, меняет code на токены, запрашивает identity (`/helix/users`), сохраняет аккаунт.

Scopes — минимально необходимые (список уточнить по документации Twitch на этапе 0).
Один Twitch-аккаунт — один пользователь (уникальный индекс `twitch_user_id`).

### 4.2. Источник прогресса дропсов — **главный риск**

Прогресс дропсов Twitch не отдаёт в публичном Helix API. В плане он берётся из неофициальных GraphQL-запросов.
Это значит:
- endpoint и схема могут поменяться без предупреждения;
- использование неофициального API может нарушать условия Twitch — **решить до начала разработки, подтвердить тобой**;
- при любой неясности статус = `unknown`, а не `done` (правило из плана сохраняется).

**Этап 0 — спайк (1–3 дня):** вручную снять ответы нужных запросов для одного тестового аккаунта,
сохранить их как sanitized fixtures, убедиться, что прогресс из них парсится. Если спайк не даёт данных —
MVP сводится к каталогу и ручному отметкам, и это нужно решить до этапа 2.

### 4.3. Ограничения клиента

- Retry: 3 попытки на 5xx/timeout с exponential backoff + jitter; 429 — уважать `Retry-After`.
- 401 → один refresh токена, затем статус аккаунта `expired` и понятное сообщение в UI.
- Таймаут на каждый remote-call — 5 с (Vercel Hobby ограничивает длительность функции, поэтому батч на один запуск коротки).

## 5. Модель данных (минимум)

```text
users              id, name, token_hash (unique), created_at
twitch_accounts    id, user_id (fk), twitch_user_id (unique), login, display_name,
                   access_token_enc, refresh_token_enc, token_expires_at,
                   status (pending|active|expired|revoked|error), last_synced_at
campaigns          id, kind (drop|badge), external_id (unique), name, game_name,
                   image_url, starts_at, ends_at, required_minutes, last_seen_at
progress           id, account_id (fk), campaign_id (fk), minutes_watched, status
                   (not_started|in_progress|claimed|expired|unknown), source (twitch|manual),
                   fetched_at, unique(account_id, campaign_id)
sync_runs          id, account_id (nullable), started_at, finished_at, status
                   (ok|partial|failed), error_code, error_summary (без секретов)
```

- `campaigns` — общий каталог, одинаковый для всех пользователей. Синхронизируется раз в 15–30 минут.
- `progress` — только по аккаунтам; `fetched_at` показывает актуальность (в UI — «обновлено 12 мин назад»).
- `sync_runs` — журнал; заменяет `tasks`, `task_runs` и `audit_logs`. Хранить 30 дней.
- Аудит «значимых действий» в MVP — это записи `sync_runs` плюс события подключения/отключения аккаунта (action + user_id) в той же таблице через `error_code = null`. Отдельная таблица — на этап 6.

## 6. Синхронизация

### 6.1. Как это работает

1. GitHub Actions по расписанию (каждые 15 минут, ориентир; Actions может задерживать запуск) делает
   `POST https://<app>.vercel.app/api/internal/sync` с заголовком `Authorization: Bearer ${CRON_SECRET}`.
2. Эндпоинт:
   - берёт не более N аккаунтов, у которых `last_synced_at` старше порога (например, 15 минут);
   - по каждому: обновляет токен при необходимости → запрашивает каталог (раз за запуск) и прогресс → `upsert` в `progress`;
   - пишет строку в `sync_runs`.
3. Один запуск укладывается в лимит Vercel. Если аккаунтов много — следующий запуск заберёт остальные.
4. Ручная синхронизация: кнопка «обновить» на карточке аккаунта → `POST /api/accounts/[id]/sync` (только один аккаунт).

### 6.2. Защита от дублей

- Concurrency в workflow (`concurrency: sync`, `cancel-in-progress: false`) — не более одного запуска сразу.
- `progress` и `campaigns` обновляются через `upsert` по уникальным ключам — повторный запуск безопасен.
- Блокировка на аккаунт: поле `locked_until` в `twitch_accounts`; занятый аккаунт пропускается.

### 6.3. Что делается без расписания

- Отключение аккаунта: удаляются токены (`*_enc = null`), статус `revoked`; строки `progress` сохраняются для истории.
- Истёкшие токены: статус `expired`, в UI — кнопка «подключить заново».

## 7. API (минимум)

| Метод | Endpoint | Назначение |
|---|---|---|
| POST | `/api/auth/login` | Вход по токену |
| POST | `/api/auth/logout` | Выход |
| GET | `/api/me` | Текущий пользователь |
| GET | `/api/accounts` | Аккаунты пользователя |
| GET | `/api/twitch/authorize` | Редирект на Twitch OAuth |
| GET | `/api/twitch/callback` | OAuth callback |
| DELETE | `/api/accounts/[id]` | Отключить аккаунт |
| POST | `/api/accounts/[id]/sync` | Ручная синхронизация |
| GET | `/api/accounts/[id]/progress` | Прогресс дропсов/значков |
| GET | `/api/campaigns?kind=drop\|badge` | Каталог |
| POST | `/api/internal/sync` | Для GitHub Actions, только с `CRON_SECRET` |

Ошибки — единый формат `{ "error": { "code", "message" } }`, без stack trace. Коды стабильны.

```text

TWITCH_CLIENT_ID
```

Секреты — в Vercel env и в GitHub Actions secrets. В репо — только `.env.example`.
Приложение не стартует без обязательных переменных (проверка при старте).

## 10. Тесты и качество

- Unit: парсинг прогресса по fixtures, расчёт статуса, шифрование (round-trip + проверка, что порча ciphertext ломает расшифровку), хэш токена, дедупликация upsert.
- Integration: БД через Neon dev-branch или локальный Postgres (docker compose с одним сервисом).
- Twitch — мок через fixtures, без живых запросов в CI.
- E2E (опционально, после MVP): Playwright, сценарий «вход → подключение (тестовый аккаунт) → дашборд».
- CI (GitHub Actions): lint, typecheck, unit tests, build. Миграции — отдельным шагом.

## 11. Этапы

### Этап 0. Спайк и каркас — 1 неделя
- Репозиторий, Next.js + TypeScript + Tailwind, Neon, миграции.
- **Спайк Twitch-прогресса** (см. 4.2). Решение: продолжаем или сужаем MVP до каталога.
- Решение по условиям использования Twitch-данных (твоё решение).

**Критерий:** `npm run dev` поднимает пустой сайт, CI зелёный, спайк дал ответ «данные парсятся» или «не парсятся».

### Этап 1. Вход по токену — 3–5 дней
- Скрипт создания пользователя, login/logout, middleware проверки cookie.
- Тесты: неверный токен, истёкшая cookie, чужой `user_id` не виден.

**Критерий:** знакомый входит по токену, без токена страницы закрыты.

### Этап 2. Twitch OAuth и аккаунты — 1 неделя
- Authorize/callback с PKCE и state-cookie, шифрование токенов, CRUD аккаунтов, лимит 5.
- Отключение аккаунта.

**Критерий:** аккаунт подключается, токены в БД зашифрованы, в логах и ответах их нет.

### Этап 3. Каталог и прогресс — 1–2 недели
- Twitch-клиент (retry, таймауты, нормализация), `campaigns` и `progress`.
- Эндпоинт `/api/internal/sync`, workflow в GitHub Actions, ручная синхронизация одного аккаунта.

**Критерий:** по расписанию прогресс обновляется, повторный запуск не создаёт дубликатов.

### Этап 4. UI — 1 неделя
- Дашборд, список аккаунтов, карточка прогресса, каталог, состояния загрузки и ошибок.

**Критерий:** все маршруты из раздела 8 работают на телефоне и на десктопе.

### Этап 5. Обкатка — 3–5 дней
- Подключить 2–3 знакомых, собрать баги, поправить ошибки.
- Проверить, что `expired`-токены и лимит Vercel обрабатываются корректно.

**Критерий:** знакомые пользуются неделю без ручного вмешательства.

**Ориентир по времени:** 4–6 недель по вечерам для одного разработчика. Это оценка, а не обещание: сильно зависит от результата спайка (этап 0).

## 13. Риски (сокращённо)

| Риск | Митигирование |
|---|---|
| Неофициальный GraphQL сломается или запрещён | Спайк на этапе 0; статус `unknown`; адаптеры в одном модуле |
| Vercel Hobby: лимиты функций и трафика | Батчи по N аккаунтов; sync только по запросу для одного аккаунта; мониторинг в Vercel dashboard |
| GitHub Actions задерживает cron | Порог «устарело» в UI; ручная кнопка обновления |
| Утечка токенов | AES-GCM, токены не в логах, `.env` в `.gitignore`, secret scan в CI |
| Neon free: лимиты хранилища и compute | Retention `sync_runs` 30 дней; компактная схема |
